# 0074 — The block editor spike edits on BlockNote, over a canonical JSON body

**Date:** 2026-09-22
**Status:** Accepted

## Context

The block editor spike needs an authoring surface that feels like Notion —
a vertical stack of blocks, a slash menu to insert, drag handles to reorder,
inline formatting where you type. Three candidates were considered.

**Tiptap with its Notion-like template.** The closest match to the look, and
the most customisable. The Tiptap editor itself is MIT, and the "Simple
Editor" UI components are open source, but the Notion-like template
specifically requires a paid Start plan. For a spike that §12 of the build
brief says is deleted afterwards, that is procurement friction bought for
something with a scheduled end date. Tiptap also gives a rich-text document
model, not a block model — the block layer would be ours to build, which is
most of the work the template is supposed to save.

**Lexical.** Already in the repo: `apps/form_builder` has a component-aware
editor with markdown round-trip at 0.47.0, built in a day. One stack, no new
vendor, no new licence. But Lexical is not block-based in the Notion sense
either, so the slash menu, the drag handles and the block nodes are all
bespoke — and the spike's scarce time is meant to go on configuration
blocks, not on rebuilding a shell that exists off the shelf.

**BlockNote.** MPL-2.0 for `@blocknote/core`, `/react`, `/mantine` and
`/shadcn`; only the `xl-*` packages (AI, DOCX/PDF export) are
`GPL-3.0 OR PROPRIETARY`, and the spike needs none of them. Its document
already _is_ `Block[]` with stable ids, props, content and children. Custom
blocks are declared with `createReactBlockSpec`, and a block may set
`content: "none"` and render an arbitrary React form — which is exactly the
finder, calendar and data_table case the spike exists to test. It is built
on ProseMirror and Yjs by people who also contribute to Tiptap, so it is not
a dead end.

The second question is saving. Notion autosaves, and an editor that looks
like Notion but has a Save button will be used as though it autosaves. But
§3.5 of the brief requires optimistic concurrency: every `save` passes the
`updated_at` it loaded, and zero rows affected is a `ConflictError`.

## Decision

**The spike's editing surface is BlockNote. BlockNote's document is a view;
the canonical document remains `{version, blocks, refs}` in
`content_pages.body`, and a tested adapter converts between them in both
directions.**

**Saving is a debounced autosave to `localStorage`, and an explicit Save —
the button, or `Ctrl/Cmd+S` — to Postgres.** Autosave never writes to the
database.

_(Revised 22 September 2026. This decision originally autosaved straight to
Postgres. That was wrong for a publishing tool: it made every keystroke a
publication, so a half-finished sentence was what the site served, and there
was no moment at which an author could be said to have decided anything.
Caching locally keeps the protection against a closed tab — which is all
autosave was ever really buying — while leaving publication a deliberate
act. The `ifUpdatedAt` check now happens at that deliberate moment, which is
where a conflict is actually meaningful to a person.)_

The brief rejected `localStorage` as the spike's _storage_, and rightly: its
API is synchronous, which pulls code toward synchronous reads in render
paths and `useState` initialisers. None of that applies to a draft cache. It
is read once when a document is opened and written on a timer; it is never
the source of truth, never rendered from, and never read back by anything
but the editor that wrote it.

Corollaries:

- **BlockNote editor state is never stored.** The build brief already warns
  this about Lexical — _"it carries `detail`, `format`, `mode`, `style`,
  `version` and `direction` on every node and is versioned to Lexical, not
  to us"_. BlockNote carries its own equivalents (`textColor`,
  `backgroundColor`, `textAlignment` prop defaults, and its own inline
  content shape). The warning transfers verbatim.
- **Block ids are seeded into BlockNote, not generated by it.** Our ids are
  what future diffing, commenting and per-block approval anchor to, so the
  adapter sets BlockNote's `id` from ours. The `data-id` this puts in the
  DOM is what the E2E suite addresses blocks by, which makes "ids were not
  reassigned" an assertion the selectors make for free.
- **"Saved" means one thing: it is in Postgres.** Anything a local draft is
  holding still reads as unsaved, because the site is not serving it. The
  status says so explicitly — "Unsaved changes · draft kept in this
  browser" — rather than letting a cached draft masquerade as a save.
- **A restored draft is announced, not applied silently.** Reopening a
  document with a cached draft restores it, says so, and offers to discard
  it. `ifUpdatedAt` still carries the `updated_at` the draft was based on,
  so a draft that has gone stale against someone else's write surfaces as a
  conflict at Save rather than overwriting them.
- **A rejected save leaves the document visibly dirty** and the stored row
  untouched, so the site keeps serving the last good version.
- **Every block's settings live in one popover**, opened from "Edit" above
  "Delete" in the block's own menu. Moving prose into the document took the
  old per-block forms with it, and with them the things that are not text: a
  heading's anchor, a notice's variant, and every configuration block's
  entire contents. One route to "everything about this block that is not its
  words" is more discoverable than the bespoke affordance per block type
  that the split pane had.
- **The slash menu is the closed palette.** §3.6 of the brief says the
  insert menu _is_ the content model made visible; a `/` menu restricted to
  the nine types states that more strongly than a dropdown does.
- **The accessible path is the primary one.** Reorder must work from the
  keyboard and the slash menu must be a real `listbox` with roving
  selection. Drag handles and pointer affordances are additions on top,
  never the only route. Notion-like editors routinely fail here and this is
  a service under the Barbados Service Standards.
- **The block model should gain `children`.** BlockNote nests natively, and
  §10 of the brief asks for nested lists to survive a round trip while §6's
  `ListBlock` cannot express one. None of the three seeded pages needs
  nesting, so this is recorded as a finding rather than built now.

## Consequences

The spike carries a second rich-text stack alongside `form_builder`'s
Lexical for as long as it lives. That is accepted because both are
throwaway-scoped: the spike is deleted per §12, and what survives it is
`packages/block-kit` — the format, the validation rules and the renderer —
none of which imports BlockNote. If the block editor is later taken to
production, choosing between BlockNote and Lexical is a decision to make
then, with the adapter as the seam that makes it possible.

The adapter is now the highest-risk piece of code in the editor, because
every round-trip guarantee runs through it. `prose-round-trip.spec.ts` is
written against it in both directions: the seeded documents prove it reads
correctly, and typing an em dash and a bold run through the editor proves it
writes correctly, which is the direction that actually loses data.
